Ansible Network Compliance Checker

An Ansible-based security auditing solution for Cisco IOS routers and switches, built and tested in a Cisco Modeling Labs (CML) environment.

Overview

While configuring networks, network engineers are prone to making mistakes in the configuration. These mistakes can introduce security vulnerabilities, such as leaving services like HTTP or Telnet enabled. Such misconfigurations can pose significant security risks. That is why organizations implement security compliance standards and perform regular audits to ensure their network devices comply with security requirements. As networks grow, manual compliance checks become time consuming and error prone. Automation enables faster, more consistent, and scalable audits.

Purpose

The project is an Ansible based network compliance checker built to automate security auditing across Cisco IOS routers and switches. The goal is to replace manual device by device inspection with a repeatable, automated process that checks each device against a defined security policy and reports any violations. This project was built as a hands-on automation exercise using a CML lab environment.

What is Ansible really?

Originally, Ansible is used to automate Linux machines. For example, instead of doing updates on each Linux host manually, Ansible can automate this task in one script. Later however, modules have been developed specifically to automate network devices. In my case, they are Cisco IOS modules.

Ansible uses a YAML file which is a human readable text file that defines how data is structured. In this case, how Cisco configuration is structured. Each Ansible script has something called a "playbook". each playbook has a set of tasks that are executed in order from top down. For example, we might have a playbook that has tasks to configure switches only and another playbook that has tasks to configure BGP or to configure ACL's and so on. In this project, I only have one playbook with multiple tasks as will be explained in a bit.

Another important Ansible file is the inventory file typically stored with the .ini extension. It contains the management IP addresses of the target devices that Ansible will connect to for automation.

Finally, Ansible uses Jinja2 templates to generate structured reports looping through each device and formatting the pass/fail result of every compliance check into a readable output file.

As shown below, each play book must have a name. and it is called "Compliance Checker". In the hosts field, I put the group names which were defined in the inventory explained earlier. So the playbook will apply all its tasks to all devices in the hosts by default unless I put a condition in one of the tasks. I also defined 2 variables. compliance score and total_checks which will be used in compliance scoring. Indentations in YAML file is critical. any wrong indentation or extra space, Ansible wont work. Then, under the "tasks, we will start listing our tasks:

compliance_checker.yml
- name: Compliance Checker
  hosts: switches:routers
  gather_facts: false
  vars:
    complince_score: 0
    total_checks: 0
  tasks:

Telnet Compliance Check

The first task below is doing a compliance check number one which is "Telnet must be disabled". Basically, each compliance check will likely have two tasks. one for gathering information from the connected device and the other will check on the results of those information.

telnet_check task
#====Remote Access Hardening complince====#

    - name: gathering secutity configuraion
      ios_command:
        commands:
        - show running-config | include transport input
      register: security_check

    #======checking SSH/telnet complince======#

    - name: SSH/Telnet complince
      block:
        - name: checking if telnet is not configured
          assert:
            that:
              - "'telnet' not in security_check.stdout[0] | lower"
              - "'all' not in security_check.stdout[0] | lower"
            fail_msg: "FAIL {{ ansible_net_hostname }}: telnet is configured"
            success_msg: "PASS {{ ansible_net_hostname }}: telnet is not configured"
          register: telnet_check_result

The first task "gathering secutity configuraion" will use a module for IOS cisco called "ios_command". It allows me to connect to the device and run the command show running-config | include transport input in CLI. Last line of the task is "register". What it does is save the output of the command we ran inside the device under the name "security_check".

The next task, We are inspecting the "security_check" output we just got from the pervious task. In Cisco CLI, when running show running-config | include transport input, if Telnet is enabled, the output will either be:

A- transport input all (both SSH and Telnet are enabled)

or

B- transport input telnet ssh (or only Telnet if no SSH configured)

"security_check" will contain either of those outputs so in this task, i put two conditions. If the word "all" or "telnet" is found in the output. The fail message will be triggered. Otherwise, it will pass.

So the fail or success message will be yet again saved in another output called "telnet_check_result" using "register". The below compliance task will check if this output is pass or fail. pass will update compliance_score by adding 1 and if it is a fail, it will leave compliance_score as is. total_checks will be added by 1 for each task regardless of the result because it is the total score. This task is repeated after each compliance check tasks:

score update
#====updating_complince_score=====#

        - name: calculating complince score
          set_fact:
            complince_score: "{{ complince_score | int + (1 if telnet_check_result is succeeded else 0) }}"
            total_checks: "{{ total_checks | int + 1 }}"

The rest of the tasks follow the same patterns. first gathering information, then evaluating the output and updating the compliance score.

Report Generation

Finally, the last two tasks are related to compliance report generation. The first task gathers the current date and time during script run. This information is important because every compliance report must include a timestamp indicating when the audit was performed. During each run, Ansible records the current date and time from the control node (the host running Ansible).

timestamp task
#=========time sync of ansible with my local machine time=========#

 - name: Gather current time from control node
      ansible.builtin.setup:
        filter: ansible_date_time
      delegate_to: localhost
      run_once: true

The final task generates the compliance report using Ansible's template module. The module takes the Jinja2 template file (compliance_report.j2), replaces the variables with the collected compliance results, and writes the final report to the specified destination path. If you would like to view the report header before running the script, it can be found in compliance_report_header.j2 in my GitHub.

report generation

    - name: Generate compliance report
      ansible.builtin.template:
        src: complince_report.j2
        dest: "/home/ahmed/projects/complince_report.j2"
